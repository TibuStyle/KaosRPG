1. VISIÓN Y CORE LOOP
RPG web cooperativo con identidad/assets propios o licenciados, inspirado en
Dungeons & Dragons y Baldur's Gate 3. El juego es SIEMPRE asíncrono y persistente.
No existe selector de Ritmo de Turnos ni alternativa en vivo.
La arquitectura es una cola de turnos ininterrumpible: espera indefinidamente al
participante actual. No salta por desconexión, inactividad o reinicio.
Host (Director) primero; jugadores por orden de unión; avance circular únicamente
cuando la acción guardada recibe una narrativa válida y ambas se confirman en DB.
El host escribe el planteamiento inicial en su turno; no hay apertura IA automática.

2. ESTRUCTURA Y CÓMO PROBAR
Raíz: server.js, db.js, approval.js, package.json, .gitignore, .env.example,
README.md, Verification.txt, Patch_Notes.txt, Patch_Notes_v1.4.txt y workflow Pages.
Frontend: public/index.html, public/style.css, public/main.js. Pruebas bajo test/.
Node.js >=22. npm install; copiar .env.example a .env; configurar CLAVE_IA_LEGACY
solo backend y SQLITE_PATH; npm run check; npm test; npm start.
Dependencia añadida: better-sqlite3 11.10.0 (nativa); requiere binario compatible o
herramientas de compilación. SQLite crea archivo/esquema al iniciar servidor.
El entorno de entrega no dispone de Node/npm: instalación y tests Node pendientes.
No se fabrica package-lock.json; generarlo y commitearlo al instalar realmente.
GitHub Pages sirve public/; backend y volumen persistente se despliegan aparte.

3. MECÁNICAS Y CONTRATOS
CREACIÓN Y CONFIGURACIÓN
- Nombre host/jugador hasta 40; historia hasta 80; premisa 2000; líneas rojas 4000.
- Tres reglas: Magia Alta/Baja/Sin; Tono Épico/Oscuro-Letal/Cómico;
  Mortalidad Historia/Implacable. Defaults Alta, Épico, Historia.
- El ritmo no es una propiedad configurable del HTML, payload, servidor o DB.
- Códigos A-Z de seis letras únicos en SQLite. Unión solo en lobby, capacidad 8+host.
- Random sigue siendo premisa fija sin IA. Configuración visible al grupo.

PERSONAJES Y PRIVACIDAD
- Nombre hasta 60 e historia requerida hasta 6000; edición/evaluación solo en lobby.
- JSON de aprobación original validado: aprobado, mensaje_narrativo, perks, defectos.
- Estados draft/evaluating/rejected/approved, persistidos; errores no aprueban.
- Perks/defectos se guardan en traits, con FK al personaje; no en member.gm de RAM.
- Público: nombre, conexión y estado; sin historia, aprobación privada ni rasgos.
- Propietario recupera historia y aprobación por token; nunca rasgos secretos.
- Aprobación envía mundo e historia a proveedor IA anterior; narrativa envía mundo y chat público.
  No se envían tokens/hashes ni rasgos a la narración. No incluir datos sensibles.
- Validación JSON es estructural; IA no garantiza detección de prohibiciones.

SQLITE, SESIONES Y CICLO DE VIDA
- Tablas: rooms, members, sessions, characters, traits, turn_order, actions,
  messages y rate_limits. FK, UNIQUE, cascadas y operaciones atómicas.
- db.js: WAL, foreign_keys=ON, synchronous=FULL, busy_timeout=5000;
  migración transaccional inicial user_version=1, rechazo de formato más reciente.
- DB local por SQLITE_PATH, fuera de public/. Servir solo public/ como estáticos.
- Token de 256 bits en sessionStorage; sessions persiste SHA-256 para recuperar
  sin guardar token bearer en claro. No son cuentas autenticadas.
- Una sesión tiene una conexión activa; recuperar reemplaza la anterior.
- Cada arranque marca a todos offline; al reconectar, se restaura su presencia.
- Reinicio conserva salas, configuración, miembros, historias, decisiones
  completadas, rasgos, turno, acciones y chat. No se cierran salas al apagar.
- Evaluación interrumpida vuelve a draft; requiere reenviar. Acción pending pasa
  a failed y se reintenta por su autor manteniendo texto y turno.
- Eliminadas caducidad de 24 horas y reserva de 15 minutos: no hay autoexpulsión.
- Host puede borrar sala para todos. Jugador puede eliminar personaje en lobby;
  durante playing solo ausentarse/desconectarse, sin modificar la cola fijada.
- Pérdida definitiva de token puede bloquear partida: recuperación autenticada pendiente.
- Una instancia por DB. Varios procesos/réplicas NO soportados.
- Volumen persistente obligatorio en hosting; retención/backups automáticos pendientes.
- No se puede importar estado perdido de v1.3 RAM; primera DB vacía.

VISTA DE PARTIDA Y CHAT
- Inicio solo host: al menos un jugador y todos conectados/aprobados.
- playing reemplaza starting temporal; unión y edición quedan bloqueadas.
- Chat Narrativo central grande, lateral con miembros/conexión/orden, input inferior.
- Input habilitado solo al participante actual y sin acción pendiente.
- Otros ven “Esperando el turno de Jack...” o nombre correspondiente.
- Lista incluye desconectados para explicar esperas; su turno no se salta.
- Acción hasta 2000 caracteres. La acción es pública y se persiste antes de la IA.
- IA narra con JSON exacto {narrativa:string}, 1..5000 caracteres.
- Error técnico o salida inválida conserva acción y propietario del turno;
  botón de reintento solo para su autor. No hay reintentos automáticos de coste.
- Respuesta válida, mensaje IA, acción completada y avance se confirman juntos.
- id UUID + turnVersion y UNIQUE por sala/turno impiden dobles envíos/avances.
- Mismo ID y datos devuelve estado anterior; ID reutilizado con datos distintos falla.
- ACK confirma guardado; room:state publica resultado IA, turno y últimos 100 mensajes.
- chat:history permite cargar anteriores, también después del reinicio.
- No hay chat libre paralelo, salto, timeout de turno ni reordenación automática.
- Contexto IA limitado a 20 mensajes recientes; memoria narrativa extensa pendiente.
